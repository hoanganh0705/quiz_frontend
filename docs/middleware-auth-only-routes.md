# Middleware auth-only routes — inventory

> Generated by **ET-1.6-B1** and appended by **ET-1.6-B2** — Epic 1.6, Batch B.
> Source code: `quiz_frontend/src/middleware.ts`.

This file lists every URL the middleware redirects *away from* when the request has an access-token cookie present. The intent is to bounce already-authenticated users off the auth pages (`/login`, `/signup`, `/forgot-password`, `/resend-verification`, `/verify-email`) so they land on the page they were originally trying to reach, or on `/` by default.

---

## Summary

- **Auth-only routes:** 5 (see `AUTH_ROUTES` constant, line 18 of `middleware.ts`).
- **Match mechanism:** `pathname === r || pathname.startsWith(r)` per route (lines 30–32, `isAuthRoute()`). Both exact and prefix matches are caught so query strings, trailing slashes, etc. behave consistently.
- **Redirect target:** the value of the `redirect` query param *if it is present and not the same path*; otherwise `/` (lines 58–68).
- **Authentication signal:** presence of the access-token cookie (`getAuthTokenFromRequest(request)`). The cookie is **not** cryptographically verified — see the JSDoc header at the top of `middleware.ts`.

## Redirect resolution rule (ET-1.6-B2)

**Rule (one-sentence form).** When an authenticated request lands on an auth-only route, the middleware redirects to the value of the `redirect` query param *if and only if* `redirect` is present and its parsed pathname differs from the current pathname; otherwise the redirect target is `/`.

### Worked examples

The rule produces the following outcomes for each row in the inventory above:

| Example URL (authenticated user lands here) | `?redirect=` value | Resolved target | Code path |
|---|---|---|---|
| `/login`                       | _absent_         | `/`             | defaults to `/` (line 67) |
| `/login`                       | `/my-profile`    | `/my-profile`   | non-self redirect (lines 60–64) |
| `/login`                       | `/login`         | `/`             | self-path rejection (line 62) → falls through to default (line 67) |
| `/signup?redirect=/settings`   | `/settings`      | `/settings`     | non-self redirect (lines 60–64) |
| `/forgot-password?redirect=/`  | `/`              | `/`             | non-self redirect — but `dest.pathname` equals `/`, which is not the current `/forgot-password`, so it *does* redirect to `/` explicitly. Equal outcome to the default. |
| `/forgot-password?redirect=/forgot-password` | (same path) | `/`             | self-path rejection (line 62) → falls through to default |
| `/verify-email`                | _absent_         | `/`             | defaults to `/` (line 67) |
| `/resend-verification?redirect=//evil.example.com/x` | external URL | `/`             | `new URL(redirectParam, request.url)` resolves scheme-relative URLs **against `request.url`**, so `//evil.example.com/x` becomes an absolute URL on a different host. **Behavior in this edge case is not explicitly tested in ET-1.6-B2** — see Finding F1. |

### Code reference

The rule is implemented in `middleware.ts` lines 58–68, inside the `middleware()` function:

```ts
if (isAuthRoute(pathname) && isAuthenticated) {
  const redirectParam = request.nextUrl.searchParams.get('redirect')
  if (redirectParam) {
    const dest = new URL(redirectParam, request.url)
    if (dest.pathname !== pathname) {
      return NextResponse.redirect(dest)
    }
  }
  // Default redirect for authenticated users on auth pages
  return NextResponse.redirect(new URL('/', request.url))
}
```

### Findings

#### Finding F1 — open-redirect surface (informational, deferred)

The `new URL(redirectParam, request.url)` call resolves any string against the current request URL. Protocol-relative values (`//host/path`) and absolute URLs (`https://host/path`) are *normalised* by the URL parser: the destination `URL` object resolves them as absolute, and `dest.pathname` is set to the host's path. In practice this means a maliciously-crafted `?redirect=//evil.example.com/x` could result in `dest.pathname === '/x'` (which is not the same as the current `/login`), so the middleware would issue a redirect to an attacker-controlled host.

**Recommended action (deferred).** A future ticket should add `dest.origin === new URL(request.url).origin` as a precondition for honouring `redirect`, falling back to `/` if the origin differs. This is a real security improvement but is **out of scope for ET-1.6-B2** (this ticket is read-only and produces documentation only). Tracked as a Phase-2 ticket.

### Deviation between code and documentation

None — the documentation above matches the code exactly. The default redirect target is `/` (line 67, literal `new URL('/', request.url)`).
